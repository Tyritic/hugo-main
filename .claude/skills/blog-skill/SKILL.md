# Blog Skill

## Overview

这个 skill 只服务于你的个人博客仓库，默认面向 `E:\MyBlog` 下的 Hugo 文章内容。

目标不是做通用 Markdown 润色，而是让博客文章在目录结构、front matter、图片使用、短代码、标题层级和展示风格上保持和现有仓库一致。

## When to Use

在以下场景使用：

- 新建博客文章
- 修改 `E:\MyBlog\content\post` 下的现有文章
- 为已有文章补充内容、图片、代码块、引用或数学公式
- 优化博客排版、标题结构、列表、图片布局、短代码使用
- 修复 front matter、文件命名、文章语言文件等博客仓库约定

不要在以下场景使用：

- 普通 Markdown 文档编辑
- 技术文档、设计文档、规范文档整理
- 与 `E:\MyBlog\content\post` 无关的写作任务

## Repository Conventions

### Post Location

- 博客文章目录：`E:\MyBlog\content\post`
- 单篇文章通常放在：`E:\MyBlog\content\post\<文章目录>\index.zh-cn.md`
- 英文文章可使用：`index.en.md`
- 文章配图、示意图、截图默认与文章 Markdown 文件放在同一目录

### Front Matter

编辑或新建文章时，优先保持如下字段完整：

```yaml
---
date : '2025-01-01T08:00:00+08:00'
draft : false
title : '文章标题'
image : ""
categories : ["分类"]
tags : ["标签"]
description : "文章摘要"
---
```

补充规则：

- `date` 使用现有仓库风格的 ISO 时间字符串，保留 `+08:00`
- `draft` 除非用户明确要求草稿，否则不要擅自改成 `true`
- `title` 与文章主题一致，通常与目录名接近，但以文章实际标题为准
- `image` 默认允许为空字符串；只有用户明确指定站点头图时才填写
- `categories` 和 `tags` 使用数组格式，即使只有一个值也保持数组
- `tags` 允许为空数组 `[]`，tag 为空属于正常情况，不要因此报错或要求补充
- 当文章包含数学公式时，可以增加 `math : true`
- 不要凭空添加仓库中未见过的 front matter 字段

## Workflow

1. 先确认目标文件是否在 `E:\MyBlog\content\post` 下；如果是新增文章，默认创建到 `content/post/<文章目录>/index.zh-cn.md`
2. 编辑前先查看 `E:\MyBlog\content\post\博客使用指南\index.zh-cn.md`
3. 判断任务类型：新建、续写、重写、美化、格式修复、补图、补短代码
4. **每次涉及博客操作时都必须检查是否符合美化标准**：
   - 标题 emoji：每一级标题都有带有语义的 emoji，且所有标题的 emoji 不重复；**emoji 不能为乱码（如 `�`）**
   - 分割线：在主要章节之间添加分割线
   - 图片：使用居中对齐和适当的宽度百分比
   - 列表格式：无序/有序列表正确使用
   - 代码块：使用正确的语法高亮
   - **tag 不修改**：美化时不对 tag 进行修改和填充操作，tag 保持原样
5. **新建博客时还必须**：
   - 为所有标题添加适当且不重复的 emoji 图标
   - 如果根据图文资料新建，必须下载图片到本地目录并更新引用路径
6. 如果当前会话可正常调用 `Sequential Thinking` MCP，则在以下任务中优先先用它拆解步骤：新建整篇文章、大规模重构章节、批量补图、从资料整理成长文、同时处理结构和排版
7. 检查 front matter 是否齐全（**不检查 tags**，tag 保持原样），再检查正文结构
8. 优先延续当前文章已有风格，不强行替换成另一套排版习惯
9. 完成后做一次完整检查：front matter、标题层级、标题 emoji（语义和重复性）、列表、图片、代码块、短代码、语言文件命名、美化标准

如果 `Sequential Thinking` 当前不可调用，退化为本地分步规划，不要因此中断博客任务。

## SequentialThinking Dependency

- 该 skill 依赖 `Sequential Thinking` MCP 来处理复杂博客任务的步骤拆解和结构规划
- 只有在当前会话中该 MCP 工具可正常调用时，才把它作为前置步骤
- 简单编辑、小修小补、单段续写、局部格式修复不需要默认调用它
- 如果 MCP 启动异常、会话未挂载该工具、或 stdio 传输不稳定，则改为本地分步规划并继续执行

## Content Structure Rules

### Headings

- 标题层级保持连续
- 不要静默修改可能带有作者意图的跳级标题
- 如果文章从 `##` 直接跳到 `####`，且看起来像误写，优先小幅修正；如果结构意图不清楚，再询问
- 默认给每个标题添加 emoji，并保证同一篇文章里的标题 emoji 尽量不重复
- emoji 需要符合标题语义，不要随机装饰；例如原理用 `🧠`、结构用 `🏗️`、流程用 `🔄`、示例用 `🧪`、总结用 `📝`
- 如果文章标题很多，优先保证同级标题之间的 emoji 不重复；在语义冲突时，语义准确优先于绝对不重复

### Emoji Priority Table

为标题选择 emoji 时，先判断标题语义，再判断标题层级，最后才考虑视觉分散度。优先级如下：

| 优先级 | 适用语义 | 推荐 emoji |
|---|---|---|
| 1 | 定义、概念、原理、本质 | `🧠` `📖` `🔍` |
| 2 | 架构、结构、组成、模型 | `🏗️` `🧩` `🗂️` |
| 3 | 流程、步骤、执行过程、生命周期 | `🔄` `🛠️` `⚙️` |
| 4 | 示例、案例、演示、实战 | `🧪` `💡` `🎯` |
| 5 | 对比、区别、优缺点、选型 | `⚖️` `🆚` `📊` |
| 6 | 注意事项、陷阱、常见问题、错误 | `⚠️` `🚨` `❗` |
| 7 | 总结、结论、复盘、建议 | `📝` `✅` `📌` |
| 8 | 数学、公式、推导、证明 | `📐` `∑` `🧮` |
| 9 | 代码、实现、接口、命令 | `💻` `⌨️` `🔧` |
| 10 | 数据、图表、统计、性能 | `📊` `📈` `📉` |

层级选择建议：

- `##` 优先使用更稳重、概括性的 emoji，如 `🧠` `🏗️` `🔄` `⚖️` `📝`
- `###` 优先使用具体功能型 emoji，如 `💡` `🧪` `🔧` `📐`
- `####` 及以下优先使用更轻量的细分 emoji，如 `📌` `🔹` `✅` `❗`

去重规则：

- **所有级别标题必须严格去重**：全文所有级别的标题 emoji 都不允许重复
- 同级标题禁止连续复用同一个 emoji
- 同一语义簇内可轮换使用备选 emoji
- 如果标题本身已非常明确，优先保留语义准确，不为了去重而换成不贴切的 emoji

### Paragraph Rhythm

- 教程类内容优先使用"概念解释 -> 示例 -> 结论/注意点"的节奏
- 连续大段文字应适当拆分，避免单段过长
- 插图之间尽量加解释文字，不要形成纯图片堆叠
- 在主要小节之间默认加入 `---` 分割线，提升阅读节奏
- 不要在过短的小节、紧邻的子标题组、列表项之间机械插入分割线，避免页面被切碎

### Lists

- 并列信息使用无序列表
- 有先后依赖的步骤使用有序列表
- 保持列表标记和缩进一致

### Terms and Formatting

- 关键概念在有助于扫读时再加粗，不要满篇强调
- 命令、路径、文件名、标识符、API、字段名使用行内代码
- 不要把每一句都格式化成"粗体 + 行内代码"

## Images and Media

- 图片默认放在文章目录下，引用相对路径文件名
- **新建博客时的图片处理**：当根据现有内容（如图文资料、参考博客、文档等）新建博客时，**必须**：
  1. 从源内容中提取所有图片链接
  2. 下载图片到目标博客文章的目录中
  3. 更新 Markdown 文件中的图片引用路径为本地相对路径
  4. 确保图片文件名唯一，避免与现有图片冲突
- 必须补充可读的 `alt` 文本
- 优先兼容仓库现有写法；如果只是普通插图，默认允许使用 HTML `img` 标签
- 图片宽度不要写死；根据图片内容密度、原始尺寸和可读性选择合适的百分比宽度
- 一般可参考：大图或流程图用 `80%` 到 `90%`，中等示意图用 `65%` 到 `80%`，小图或局部截图用 `45%` 到 `65%`
- 当图片中文字较多、细节较密时，优先给更大的宽度；当图片本身较小或需要与正文保持节奏时，使用更保守的宽度
- 当图片需要更稳定的展示宽度时，优先使用现有仓库已存在的样式模式，例如：

```html
<div align="center">
  <img src="example.png" alt="示意图说明" width="82%">
</div>
```

- 如果文章已统一使用 `style="zoom:..."`，可继续沿用；如果在新内容里需要更稳定的响应式效果，优先使用 `width="xx%"`
- 只有在明确提升可读性时才改成居中容器写法，不要把旧文章里的所有图片批量替换掉

### Image Width Decision Table

按图片类型优先判断宽度：

| 图片类型 | 特征 | 推荐 width |
|---|---|---|
| 架构图 / 流程图 | 线条多、节点多、文字密 | `82%` 到 `92%` |
| 原理示意图 | 结构清晰、信息中等 | `72%` 到 `85%` |
| 表格截图 | 文字较多、横向信息密集 | `85%` 到 `95%` |
| 代码截图 | 字号小、细节密集 | `80%` 到 `90%` |
| 局部界面截图 | 聚焦单一区域 | `55%` 到 `70%` |
| 小型图标 / 结果图 | 信息少、主要起点缀作用 | `40%` 到 `55%` |
| 对比图（两张分别展示） | 需要节奏感和留白 | 每张 `45%` 到 `60%` |
| 数学推导配图 | 公式或符号较密 | `75%` 到 `88%` |

细化规则：

- 图片中文字越多，宽度越大
- 图片越宽、横向内容越多，宽度越大
- 只是辅助说明的小图，不要给到接近满宽
- 如果同一节连续出现多张图，优先做宽度区分，避免视觉上全部一样重
- 同一篇文章里，相同类型的图尽量保持接近的宽度区间
- 无法判断时，默认从 `78%` 开始，再根据图中文字密度上调或下调

## Code Blocks and Math

- 代码块必须使用 fenced code block
- 语言明确时一定补 language tag
- 示例代码要能独立阅读，不要裁剪到失去上下文
- 行内公式使用 `$...$`
- 独立公式使用 `$$...$$`
- 文章里出现较多公式时，确认 front matter 含 `math : true`

## Hugo-Specific Patterns

优先复用仓库已有内容形式：

- 引用短代码：`quote`
- B 站视频短代码：`bilibili`
- 提示块短代码：`notice`

如果用户要插入这些内容，优先保持与 `博客使用指南` 中相同的写法，不要自行发明新短代码格式。

## Language File Rules

- 中文文章默认使用 `index.zh-cn.md`
- 英文文章默认使用 `index.en.md`
- 若同一篇文章已有中英文双语文件，编辑时只改用户指定的语言版本
- 不要未经要求同步翻译另一语言文件

## Content Safety Rules

- 不要编造技术事实、实验结果、源码行为、性能数据或引用来源
- 不要擅自统一术语，除非用户明确要求
- 不要只做正文润色而忽略 front matter 和目录结构
- 不要把博客文章改写成文档站说明书风格，除非用户明确要求

## Done Criteria

任务完成前，确认以下事项：

- 目标文件位于正确的博客目录
- front matter 字段与当前仓库风格一致
- 标题层级、列表、图片和代码块格式没有明显破坏
- **每次操作都必须检查**：标题 emoji（每级都有且语义相关、所有级别严格不重复、不能为乱码如 `�`）、分割线、图片宽度、列表格式、代码块格式等美化标准；**tag 不修改**
- 文章引用的图片或资源路径有效且位于文章目录中
- **新建博客时额外检查**：如果文章包含外部图片链接，确认已下载到本地并更新为相对路径
- 若使用数学公式、短代码或语言文件命名，符合现有博客仓库约定
